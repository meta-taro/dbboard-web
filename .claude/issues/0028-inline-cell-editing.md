# 0028 — Inline cell editing: SQL the user did not type

## Purpose

Rung 6 is the write paths. It mirrors five desktop ADRs:

| Desktop         | Subject                                        | Ledger status                                      |
| --------------- | ---------------------------------------------- | -------------------------------------------------- |
| ADR-0042        | Inline cell editing — the pure write-back core | `todo` — "largest single rung"                     |
| ADR-0063        | Inline cell editing wired into the Tauri app   | not in the ledger (postdates the survey)           |
| ADR-0049 / 0050 | Logical dump                                   | `todo` — sets `has_table_ddl`                      |
| ADR-0051        | Restore                                        | `todo` — sets `has_execute` + `has_atomic_restore` |
| ADR-0045        | Local column/table annotations                 | `todo`                                             |

Re-deriving the rows against both codebases (baseline §19: the shipped code is
the authority, the ledger row is a hypothesis) changed the premise of the rung
itself, retired one row, and split the rest in two. **This ticket is rung 6a —
inline cell editing only.** Dump and restore become ticket `0029`; annotations
are `n/a` and close with the rung. The corrections are below in full, because
they are the more useful artifact.

## What the survey got wrong

### Web is not read-only, and never has been

The ledger says rung 6 "gives web a write path it has never had", and
`project-status.md` calls read-only "a real safety property to give up
deliberately rather than by drift". Both are false, and the second is exactly
backwards: the property was never held, so there is nothing to give up.

`ExecuteQuery` (`apps/api/src/usecase/execute-query.use-case.ts`) enforces one
rule and it is not about writes:

```ts
const result = await this.resolveAdapter(connectionId).executeQuery(sql);
if (result.rows.length > ROW_CAP) {
  throw new QueryError(`result exceeds the 10,000-row cap (…)`);
}
```

`QueryRequestDto` validates `@IsString() @IsNotEmpty()` and nothing else. And
`PostgresAdapter.executeQuery` calls `pool.query({ text: sql, rowMode: "array" })`
with no `values`, so node-postgres uses the **simple** query protocol — which
means `POST /connections/:id/query` today runs `UPDATE`, `DROP`, and the
multi-statement batch `SELECT 1; DROP TABLE t`. A grep for a classifier across
`apps/`, `docs/` and `.claude/decisions.md` returns only TypeScript `readonly`
modifiers.

**This is not a contract divergence.** Desktop's HTTP server has no classifier
either — `crates/dbboard-server` contains no reference to `read_only` at all.
`read_only.rs` guards `DatabaseAdapter::query_read_only`, which the **MCP** path
and the desktop query pane use; the desktop parity table says in as many words
that lifting the write ban "applies to connection **management**, not to
arbitrary SQL". Two clients, same posture: the SQL box is the user's, and the
agent surface is the thing that gets policed.

So the rung's actual subject is narrower and sharper than the ledger's framing.
Rung 6 does not add the first write. It adds **SQL the user did not type** —
generated by a cell editor, or read out of a file by a restore. That is why
ADR-0042 has a `rows_affected == 1` gate and ADR-0051 has an empty-target gate:
neither exists to stop a write, both exist because nobody read the statement
before it ran. That is the property this rung must protect, and it is a property
web genuinely does not have yet.

### The shipped authority is ADR-0063, not ADR-0042

ADR-0089 retires the egui client — "Tauri is the only client" — and the desktop
parity table re-ports the rung-6 ADRs accordingly: 0042 → **ADR-0063**, 0049/0050
→ ADR-0064, 0051 → ADR-0065. Under §19 the mirror target is the shipped port.

That narrows the work, in web's favour. ADR-0042 allows two row identities:
a declared primary key, or SQLite's `rowid`. ADR-0063 decision 2 keeps only the
first — editable requires `describeTable` to report a non-empty `primary_key`,
and a rowid-only SQLite table renders a read-only note instead. Web ships one
engine family (Postgres) and `RowIdentity::resolve` already refuses Postgres
without a PK, so the `SqliteRowid` variant would be dead code on arrival. It is
not ported. `RowKey` collapses to the `Columns` case, which is why this ticket's
`RowKey` is a plain array rather than a union.

What does port verbatim is the escaping, because it is the part that is unsafe
to re-derive: identifiers delimiter-quoted with the delimiter doubled; edited
values as single-quoted literals with `'` doubled, or the bare keyword `NULL`;
identity values encoded **by their real type** (bare number / quoted text /
`IS NULL`) rather than round-tripped through text; blob identity refused.
Postgres needs no backslash doubling — that branch is MySQL's, and arrives with
ADR-0068 in rung 7.

### Web has no anchor for the editability gate

ADR-0063 decision 2 gates editing on provenance, not on the SQL: editable only
when the grid came from a sidebar **browse** carrying the source `TableInfo`,
and never from an arbitrary query, because a `SELECT` cannot be trusted to name
the table it reads.

Web has no browse. `SchemaBrowser.vue` declares
`defineEmits<{ (event: "insert", text: string): void }>()` and nothing else; the
SQL page splices the identifier into the editor at the caret and the user runs
whatever they then type. `useQueryExecution` stores `QueryResult` and no
provenance. So the precondition ADR-0063 assumes is itself a slice — the same
shape as rung 4, where the capabilities row turned out to need a per-connection
route before it could mean anything.

The consequence for slice ordering is that browse lands first, and it must
`SELECT *`. ADR-0063's grouping step throws when a primary-key column is absent
from the result, and desktop says why in the message: "browse with SELECT \* to
edit". A browse that projected columns would produce grids that look editable
and fail at Save.

### ADR-0045 (annotations) is `n/a`, for two independent reasons

The ADR states its own scope: "**Desktop-only / no `dbboard-web` mirror / no HTTP
contract change.** Purely local persistence and UI." That alone settles it.

The second reason matters more, because it would still hold if the ADR had said
nothing. Decision 2 keys notes on `connection id → table`, where the id is
"stable, from `connections.toml`". Web's registry is
`InMemoryConnectionRegistry`: ids are minted per process and do not survive a
restart. There is no stable anchor to key a note on, so a faithful port would
produce notes that silently detach from their tables on every deploy. Porting it
would require inventing persistence that this repo has deliberately not built
yet — which is a different decision, not this one.

The row closes as `n/a` with both reasons recorded, the same disposition rung 5
gave ADR-0073 and ADR-0074.

### ADR-0050 has no web surface, and 0049 is all catalog

ADR-0050's consequence section says it outright: "no parity impact — the
threshold is a desktop UI preference, not part of the adapter or dump contract."
ADR-0064 decision 3 confirms the shape by putting the warn threshold in
frontend-owned storage, "like theme and language". Web's equivalent is
`localStorage`, and it is a line of UI, not a rung row.

ADR-0049 is the opposite: bigger for web than the row suggests. Its DDL has two
halves — SQLite reads verbatim `sql` out of `sqlite_master`, Postgres
**reconstructs** DDL from the catalog (columns, types, NOT NULL, defaults,
identity, PK, unique, check, indexes, FKs, owned sequences). Web ships only the
Postgres family, so it inherits the reconstruction and none of the cheap path.
That is a rung of its own, and it is why dump and restore move to ticket `0029`
rather than riding along here.

## Scope

**6a (this ticket): the cell editor.** No new adapter method and no capability
flag — matching ADR-0042's "no new adapter method and no HTTP contract change",
which holds here for the same reason: the generated `UPDATE` goes through the
existing `executeQuery`, and `QueryResult.rows_affected` (already `rowCount ?? 0`
from node-postgres) is the gate.

**6b (ticket `0029`): dump and restore.** `tableDdl` + Postgres catalog
reconstruction (`has_table_ddl`), the lexical `split_statements` layer and its
degrade-open classification, `execute` / `executeInTransaction` (`has_execute`,
`has_atomic_restore`), the empty-target gate via `listTables`.

The rung numbering does not change; only the ticket count does.

## Constraints this rung inherits

Three properties earlier rungs built, all of which the cell editor can break:

- **Rung 3 — the real row index.** `useResultSort` exposes `sortedRowOrder` as a
  permutation. The third row of a sorted grid is not row 3. Staged edits key on
  the **original** index (desktop's `cellKey(row, col)` says the same: "uses the
  ORIGINAL row index … so staging survives re-sorting"), and the `WHERE` key is
  read from the original row's cells.
- **Rung 2 — the startup-packet `statement_timeout`.** A server-side timeout is
  what makes an over-budget statement stop rather than commit. This is the rung
  where that stops being theoretical: the client-side timer it replaced would
  have abandoned a write that kept running.
- **Rung 5 — an edit rebuilds the adapter.** `UpdateConnection` swaps in a
  successor adapter. Nothing on this path may hold an adapter across requests;
  resolve per request from the registry.

## Slices

- **A — browse.** `apps/web/app/utils/sql-build.ts` (pure: `quoteIdent`,
  `qualifiedName`, `selectTopN`) plus a browse action per table on
  `SchemaBrowser.vue` alongside insert. The generated SQL goes **into the editor**
  and then runs, so the user can see and re-run it, and the page records the
  source `TableInfo` beside the result. Editing the SQL box clears the
  provenance. This mirrors desktop's split exactly: browse SQL is built in the
  frontend (`src/lib/sql/build.ts`), update SQL is built in core.
- **B — the pure builder.** `apps/api/src/domain/write-back.ts`: `quoteIdent`,
  `quoteLiteral`, `qualifiedTable`, `CellValue`, `KeyColumn`, `UpdatePlan`,
  `buildUpdateSql`, `WriteBackError` (`NoEdits` / `EmptyKey` /
  `UnsupportedKeyType`). Adversarial unit tests: quotes in identifiers, quotes in
  values, empty string vs NULL, blob key, null key → `IS NULL`, deterministic
  clause order.
- **C — identity and grouping.** API-side `resolveRowIdentity(schema)` from
  `TableSchema.primary_key` (rung 4's deliverable), refusing when empty;
  web-side `apps/web/app/utils/grid-edit.ts` — `cellKey(row, col)` on the
  **original** index and `buildRowUpdates`, which refuses when a PK column is
  absent from the result columns.
- **D — usecase and route.** `UpdateRow` usecase; `POST /connections/:id/rows`
  under the already-unilateral `/connections/*` prefix so `docs/api-contract.md`
  keeps its zero diff; DTO; the `rows_affected === 1` gate with 0 and n>1 both
  errors that leave the edit staged.
- **E — the grid.** Double-click to edit, staged tint, explicit NULL affordance,
  per-cell revert and discard-all, Save; errors surface without clearing staging.
- **F — closeout.** i18n across 11 locales, an ADR in `decisions.md`, ledger and
  status updates, contract zero-diff check.

## Acceptance criteria

- A browsed table with a declared primary key is editable; an arbitrary query
  result is not, whatever it selects.
- A table with no primary key renders read-only with a stated reason.
- Saving one changed cell issues exactly one `UPDATE` and reports success only
  when one row matched. 0 and n>1 are errors and the edit stays staged.
- Sorting the grid, then editing, updates the row the user pointed at.
- `docs/api-contract.md` is untouched by this rung (see Verification for the
  baseline commit).
- Escaping is covered by tests that fail if a quote, a NULL, or a blob key is
  mishandled.
