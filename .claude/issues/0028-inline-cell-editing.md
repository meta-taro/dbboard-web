## What the survey got wrong

### Web is not read-only, and never has been

The ledger says rung 6 "gives web a write path it has never had", and
`project-status.md` calls read-only "a real safety property to give up
deliberately rather than by drift". Both are false, and the second is exactly
backwards: the property was never held, so there is nothing to give up.

`ExecuteQuery` (`apps/api/src/usecase/execute-query.use-case.ts`) enforces one
rule and it is not about writes:

```ts
const result = await this.resolveAdapter(connectionId).executeQuery(sql);
if (result.rows.length > ROW_CAP) {
  throw new QueryError(`result exceeds the 10,000-row cap (…)`);
}
```

`QueryRequestDto` validates `@IsString() @IsNotEmpty()` and nothing else. And
`PostgresAdapter.executeQuery` calls `pool.query({ text: sql, rowMode: "array" })`
with no `values`, so node-postgres uses the **simple** query protocol — which
means `POST /connections/:id/query` today runs `UPDATE`, `DROP`, and the
multi-statement batch `SELECT 1; DROP TABLE t`. A grep for a classifier across
`apps/`, `docs/` and `.claude/decisions.md` returns only TypeScript `readonly`
modifiers.

**This is not a contract divergence.** Desktop's HTTP server has no classifier
either — `crates/dbboard-server` contains no reference to `read_only` at all.
`read_only.rs` guards `DatabaseAdapter::query_read_only`, which the **MCP** path
and the desktop query pane use; the desktop parity table says in as many words
that lifting the write ban "applies to connection **management**, not to
arbitrary SQL". Two clients, same posture: the SQL box is the user's, and the
agent surface is the thing that gets policed.

So the rung's actual subject is narrower and sharper than the ledger's framing.
Rung 6 does not add the first write. It adds **SQL the user did not type** —
generated by a cell editor, or read out of a file by a restore. That is why
ADR-0042 has a `rows_affected == 1` gate and ADR-0051 has an empty-target gate:
neither exists to stop a write, both exist because nobody read the statement
before it ran. That is the property this rung must protect, and it is a property
web genuinely does not have yet.

### The shipped authority is ADR-0063, not ADR-0042

ADR-0089 retires the egui client — "Tauri is the only client" — and the desktop
parity table re-ports the rung-6 ADRs accordingly: 0042 → **ADR-0063**, 0049/0050
→ ADR-0064, 0051 → ADR-0065. Under §19 the mirror target is the shipped port.

That narrows the work, in web's favour. ADR-0042 allows two row identities:
a declared primary key, or SQLite's `rowid`. ADR-0063 decision 2 keeps only the
first — editable requires `describeTable` to report a non-empty `primary_key`,
and a rowid-only SQLite table renders a read-only note instead. Web ships one
engine family (Postgres) and `RowIdentity::resolve` already refuses Postgres
without a PK, so the `SqliteRowid` variant would be dead code on arrival. It is
not ported. `RowKey` collapses to the `Columns` case, which is why this ticket's
`RowKey` is a plain array rather than a union.

What does port verbatim is the escaping, because it is the part that is unsafe
to re-derive: identifiers delimiter-quoted with the delimiter doubled; edited
values as single-quoted literals with `'` doubled, or the bare keyword `NULL`;
identity values encoded **by their real type** (bare number / quoted text /
`IS NULL`) rather than round-tripped through text; blob identity refused.
Postgres needs no backslash doubling — that branch is MySQL's, and arrives with
ADR-0068 in rung 7.

### Web has no anchor for the editability gate

ADR-0063 decision 2 gates editing on provenance, not on the SQL: editable only
when the grid came from a sidebar **browse** carrying the source `TableInfo`,
and never from an arbitrary query, because a `SELECT` cannot be trusted to name
the table it reads.

Web has no browse. `SchemaBrowser.vue` declares
`defineEmits<{ (event: "insert", text: string): void }>()` and nothing else; the
SQL page splices the identifier into the editor at the caret and the user runs
whatever they then type. `useQueryExecution` stores `QueryResult` and no
provenance. So the precondition ADR-0063 assumes is itself a slice — the same
shape as rung 4, where the capabilities row turned out to need a per-connection
route before it could mean anything.

The consequence for slice ordering is that browse lands first, and it must
`SELECT *`. ADR-0063's grouping step throws when a primary-key column is absent
from the result, and desktop says why in the message: "browse with SELECT \* to
edit". A browse that projected columns would produce grids that look editable
and fail at Save.

### ADR-0045 (annotations) is `n/a`, for two independent reasons

The ADR states its own scope: "**Desktop-only / no `dbboard-web` mirror / no HTTP
contract change.** Purely local persistence and UI." That alone settles it.

The second reason matters more, because it would still hold if the ADR had said
nothing. Decision 2 keys notes on `connection id → table`, where the id is
"stable, from `connections.toml`". Web's registry is
`InMemoryConnectionRegistry`: ids are minted per process and do not survive a
restart. There is no stable anchor to key a note on, so a faithful port would
produce notes that silently detach from their tables on every deploy. Porting it
would require inventing persistence that this repo has deliberately not built
yet — which is a different decision, not this one.

The row closes as `n/a` with both reasons recorded, the same disposition rung 5
gave ADR-0073 and ADR-0074.

### ADR-0050 has no web surface, and 0049 is all catalog

ADR-0050's consequence section says it outright: "no parity impact — the
threshold is a desktop UI preference, not part of the adapter or dump contract."
ADR-0064 decision 3 confirms the shape by putting the warn threshold in
frontend-owned storage, "like theme and language". Web's equivalent is
`localStorage`, and it is a line of UI, not a rung row.

ADR-0049 is the opposite: bigger for web than the row suggests. Its DDL has two
halves — SQLite reads verbatim `sql` out of `sqlite_master`, Postgres
**reconstructs** DDL from the catalog (columns, types, NOT NULL, defaults,
identity, PK, unique, check, indexes, FKs, owned sequences). Web ships only the
Postgres family, so it inherits the reconstruction and none of the cheap path.
That is a rung of its own, and it is why dump and restore move to ticket `0029`
rather than riding along here.

## Scope

**6a (this ticket): the cell editor.** No new adapter method and no capability
flag — matching ADR-0042's "no new adapter method and no HTTP contract change",
which holds here for the same reason: the generated `UPDATE` goes through the
existing `executeQuery`, and `QueryResult.rows_affected` (already `rowCount ?? 0`
from node-postgres) is the gate.

**6b (ticket `0029`): dump and restore.** `tableDdl` + Postgres catalog
reconstruction (`has_table_ddl`), the lexical `split_statements` layer and its
degrade-open classification, `execute` / `executeInTransaction` (`has_execute`,
`has_atomic_restore`), the empty-target gate via `listTables`.

The rung numbering does not change; only the ticket count does.

## Constraints this rung inherits

Three properties earlier rungs built, all of which the cell editor can break:

- **Rung 3 — the real row index.** `useResultSort` exposes `sortedRowOrder` as a
  permutation. The third row of a sorted grid is not row 3. Staged edits key on
  the **original** index (desktop's `cellKey(row, col)` says the same: "uses the
  ORIGINAL row index … so staging survives re-sorting"), and the `WHERE` key is
  read from the original row's cells.
- **Rung 2 — the startup-packet `statement_timeout`.** A server-side timeout is
  what makes an over-budget statement stop rather than commit. This is the rung
  where that stops being theoretical: the client-side timer it replaced would
  have abandoned a write that kept running.
- **Rung 5 — an edit rebuilds the adapter.** `UpdateConnection` swaps in a
  successor adapter. Nothing on this path may hold an adapter across requests;
  resolve per request from the registry.

## Slices

- **A — browse.** `apps/web/app/utils/sql-build.ts` (pure: `quoteIdent`,
  `qualifiedName`, `selectTopN`) plus a browse action per table on
  `SchemaBrowser.vue` alongside insert. The generated SQL goes **into the editor**
  and then runs, so the user can see and re-run it, and the page records the
  source `TableInfo` beside the result. Editing the SQL box clears the
  provenance. This mirrors desktop's split exactly: browse SQL is built in the
  frontend (`src/lib/sql/build.ts`), update SQL is built in core.
- **B — the pure builder.** `apps/api/src/domain/write-back.ts`: `quoteIdent`,
  `quoteLiteral`, `qualifiedTable`, `CellValue`, `KeyColumn`, `UpdatePlan`,
  `buildUpdateSql`, `WriteBackError` (`NoEdits` / `EmptyKey` /
  `UnsupportedKeyType`). Adversarial unit tests: quotes in identifiers, quotes in
  values, empty string vs NULL, blob key, null key → `IS NULL`, deterministic
  clause order.
- **C — identity and grouping.** API-side `resolveRowIdentity(schema)` from
  `TableSchema.primary_key` (rung 4's deliverable), refusing when empty;
  web-side `apps/web/app/utils/grid-edit.ts` — `cellKey(row, col)` on the
  **original** index and `buildRowUpdates`, which refuses when a PK column is
  absent from the result columns.
- **D — usecase and route.** `UpdateRow` usecase; `POST /connections/:id/rows`
  under the already-unilateral `/connections/*` prefix so `docs/api-contract.md`
  keeps its zero diff; DTO; the `rows_affected === 1` gate with 0 and n>1 both
  errors that leave the edit staged.
- **E — the grid.** Double-click to edit, staged tint, explicit NULL affordance,
  per-cell revert and discard-all, Save; errors surface without clearing staging.
- **F — closeout.** i18n across 11 locales, an ADR in `decisions.md`, ledger and
  status updates, contract zero-diff check.

## Acceptance criteria

- A browsed table with a declared primary key is editable; an arbitrary query
  result is not, whatever it selects.
- A table with no primary key renders read-only with a stated reason.
- Saving one changed cell issues exactly one `UPDATE` and reports success only
  when one row matched. 0 and n>1 are errors and the edit stays staged.
- Sorting the grid, then editing, updates the row the user pointed at.
- `docs/api-contract.md` is untouched by this rung (see Verification for the
  baseline commit).
- Escaping is covered by tests that fail if a quote, a NULL, or a blob key is
  mishandled.

  `useSchemaBrowser.ts` exported its own `quoteIdent` and built the qualified

  which keeps the two in lockstep. A test pins that a failed run leaves both
  untouched, and another pins that a plain `run(sql)` clears it: whatever is in
  the SQL box at Run time is the user's text, and a `SELECT` cannot be trusted
  to name the table it reads.

The browse button sits inside the table's `<summary>`, so it carries

column probe on top of the browse. A test asserts the fetch count stays at one.

### Slices B and C — write-back SQL and row identity (2026-08-05)

Landed together because they are two halves of one seam: B builds the statement,
C decides what keys it.

**B — `apps/api/src/domain/write-back.ts`** (27 tests). The web mirror of
desktop's `crates/dbboard-core/src/write_back.rs`. It is `domain`: pure, no I/O,
no Nest decorators, because this is the one statement in the product the user
did not type and cannot proof-read before it runs, and the escaping has to be
testable adversarially in isolation.

Three refusals are throws rather than fallbacks, and each has a test:

- `EmptyKey` — an `UPDATE` with no `WHERE` rewrites the table. There is no
  degraded behaviour worth having here.
- `NoEdits` — an empty `SET` is a syntax error, and there is nothing to write.
- `UnsupportedKeyType` — a blob identity value has no safe literal form.
  Comparing against its base64 text would match a different row, so the error
  names the offending column instead.

Two escaping decisions that a reader would otherwise be tempted to "fix":

- `quoteIdent` and `quoteLiteral` escape **different** characters and are
  deliberately not folded together. `quoteIdent("o'brien")` leaves the single
  quote alone; doubling it would corrupt the name. Both directions are pinned.
- `quoteLiteral` does **not** touch a backslash. Postgres treats it as an
  ordinary character in a standard string literal
  (`standard_conforming_strings` has defaulted on since 9.1), so doubling would
  store two. MySQL is the dialect that needs it, and it arrives with ADR-0068.

The `WHERE` key encodes each value by its **real type** — bare number, quoted
text, `IS NULL` — because the identity values arrive typed from the row rather
than round-tripped through text. Edited values go the other way: always a
string literal, whatever they look like, so the engine coerces by the target
column's type. A numeric-looking edit still goes out quoted; guessing its type
here would be the client overriding the column's.

**C — identity and grouping.** `resolveRowIdentity(schema)` reads
`TableSchema.primary_key` and returns `null` when it is empty. It does not fall
back to the per-column `primary_key` flags: the two agree in practice, but only
`primary_key` is ordered, and for a composite key the wrong order is a
different key. A test pins that the fallback is absent.

`apps/web/app/utils/grid-edit.ts` (15 tests) holds the rule the module exists
for: **a staged edit is keyed on the row's original index, never its display
position.** Rung 3's `useResultSort` exposes `sortedRowOrder` as a permutation,
so the third row of a sorted grid is not row 3 — keying on the display position
would stage an edit against one row and write it to another, silently and with
no way back. `cellKey` joins the two indices with a NUL, so `(1, 23)` and
`(12, 3)` cannot collide; both the separator and the collision are tested.

`buildRowUpdates` adds one refusal desktop does not have: a staged row index
that is not in the current result throws, rather than reading a key from
`undefined` and emitting an `UPDATE` keyed on garbage. It also refuses when a
primary-key column is missing from the result columns, and the message names the
fix ("browse with `SELECT *` to edit") because the cause is three screens away
from the failure — which is why slice A's `selectTopN` emits `SELECT *` rather
than a projection.

Order of both outputs is deterministic (rows ascending by original index, edits
by column index) so the payload does not depend on which cell the user clicked
first.

TDD note: the implementation of `grid-edit.ts` was written before its test — a
§4/§20 chain break. It was parked outside the tree, the test was written and
confirmed RED (module not found), then the implementation was restored to make
it GREEN. Recorded rather than quietly retrofitted.

### Slice D — usecase and route (2026-08-05)

`POST /connections/:id/rows` → `ConnectionRowsController` → `UpdateRow` →
`buildUpdateSql` → `DatabaseAdapter.execute`. Web-only surface (desktop reaches
write-back through the `update_row` Tauri command and has no HTTP route to
mirror), nested under the already-unilateral `/connections/*` prefix so
`docs/api-contract.md` keeps its zero diff against `86b324f`.

**The write primitive is its own port method.** `DatabaseAdapter.execute?(sql)`
returns the affected row count and is optional, so a driver that must not write
simply omits it and `UpdateRow` turns that absence into a `CapabilityError` —
the web equivalent of desktop's `NotEditable`. It is not folded into
`executeQuery`, which decodes a result set and asserts text wire format: a write
has no result set, and the count is the only thing worth reading back. The
shape matches desktop's `execute`, which restore (ADR-0051, rung 6b) needs too.
`PostgresAdapter` implements it and flips `has_execute`; the flag and the method
travel together, as the port says.

**A new error category.** A failed affected-row gate is not a bad request — the
client sent something well-formed and the world moved underneath it — so
`ConflictError` → **409** rather than reusing `QueryError` → 400. Same envelope,
new category; web-only, because desktop reports the gate straight into its own
UI and has no status code to choose. Desktop's two messages are mirrored
verbatim: `0` → "no row matched — it may have been changed or deleted since it
was loaded", `n` → "expected to update exactly one row but {n} matched — the key
columns are not unique".

**Build before send.** `buildUpdateSql` runs before `adapter.execute`, so a
refused plan costs no round trip. That ordering is the point for an empty key:
the alternative is learning about it from an affected count _after_ an unkeyed
`UPDATE` has rewritten the table. A test asserts `execute` was never called.

Honest limitation, inherited from desktop: this is a bare statement, not a
transaction, so a count other than 1 is only visible after the write committed.
For 0 that is harmless. For >1 it means the catalog named a "primary key" that
is not unique and several rows now hold the new value; rolling that back needs
`executeInTransaction`, which arrives with restore in rung 6b.

**The DTO validates shape; the domain validates meaning.** `UpdateRowDto`
mirrors desktop's `KeyColumnInput` / `CellEditInput`. An empty `key`, an empty
`edits`, and a blob identity value all pass validation and are refused by
`write-back.ts` by name — re-gating them here would replace those messages with
a generic 422 on a field path. `value: null` and an absent `value` both mean SQL
`NULL`; `""` stays a value, because an empty string and NULL are different rows.

Not decorated with `@UseInterceptors(HistoryRecordingInterceptor)`: history is
the record of queries the user ran, and this is a statement they never typed.
Desktop writes no history entry for write-back either, and keeps the command off
its MCP surface so external agents stay read-only — web keeps the route off the
AI tool surface for the same reason.

Integration coverage (11 tests, real Postgres via testcontainers) proves what no
mock can: the generated statement parses, the affected count comes back off the
wire, a text literal is assignment-cast into an `int` column, a
statement-shaped value (`'); DROP TABLE …; --`) lands as data with the table
still standing, backslashes survive un-doubled (confirming the
`standard_conforming_strings` assumption from slice B), a NULL identity keys on
`IS NULL`, a vanished row is 409, an unkeyed plan is 400 with the table
untouched, and a constraint violation stays a 400 `query` rather than being
relabelled a conflict.

### Slice E — the grid and the page (2026-08-05)

Double-click a cell, edit in place, Save. `ResultGrid.vue` grew an optional
`edit: EditContext | null` prop and a `saved` emit; `CellEditorDialog.vue` is
the full-value editor behind the `⤢` affordance; `useRowUpdate` is the request
loop; `useEditContext` decides whether any of it is available. The 16 shared
strings are mirrored from desktop `messages.ts` across all 11 locales (plus a
web-only `revert`, which desktop has no per-cell affordance for), so slice F's
i18n item lands here.

**Staging is keyed on the original row index, never the display position.**
`grid-edit.ts` already held that rule; the grid honours it by looking every
staged cell up through `cellKey(originalIndex, col)` and never through the
sorted position. The acceptance criterion "sort, then edit, updates the row the
user pointed at" is a test, not a hope.

**Editability is provenance, never SQL.** The page hands the grid a context
only when a browse named the table and a describe returned a key. Nothing
parses a query — a `SELECT` cannot be trusted to name the table it reads, and
guessing here writes to the wrong table.

**The context follows the rows on screen, not the click that asked for them.**
After every run the page reads provenance back out of `useQueryExecution`
(`syncEditContext`) rather than reusing the browse payload. A failed run leaves
the previous rows displayed, and those rows are still the previous table's;
using the payload would attach a new table's key to an old table's rows. This
is stricter than desktop, which clears `editTable` on failure and so leaves
rows on screen that are no longer editable at all.

**"No primary key" and "we could not ask" are different answers.**
`useEditContext.noPk` is true only when a _successful_ describe reported zero
key columns; a failed or unsupported describe leaves the grid read-only and
says nothing. Desktop swallows the describe error into an empty PK and conflates
the two, which would render "this table has no primary key" at a connection
that simply cannot introspect. Same distinction `ColumnInfo`'s optional fields
already draw.

**Errors never clear staging.** A failed save leaves every staged cell tinted
and the banner above them; `useRowUpdate` stops at the first failing row, so
what is still marked is exactly what is still unwritten. Discard clears both
the staging and the error — an error about a write that will never be retried
is a red box with no way out.

**NULL is an affordance, not a spelling.** `∅` stages SQL `NULL`; an empty
input stages `""`. The two are different rows, and the editor refuses to make
the user guess which one an empty box means.

**Save re-runs the browse, not the editor.** `onSaved` re-executes the
statement that produced the rows (`browseSql`), because the editor is a
scratchpad and refreshing a just-written grid with an unrelated draft query is
a strange thing for Save to do. Desktop's `reloadAfterSave` re-runs the editor
text; this is the one place the mirror is deliberately narrower.

One production fix fell out of the tests: `useRowUpdate` resolved the API base
at construction, which made _displaying_ a read-only grid require a Nuxt app.
It now resolves per request — a save always starts from a click, where the Nuxt
instance is a client-lifetime singleton.
