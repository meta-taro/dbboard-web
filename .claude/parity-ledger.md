# Desktop parity ledger

Maps every desktop ADR (`dbboard/docs/decisions.md`, ADR-0001 … ADR-0085 as of
`dbboard@2fab7ba`) onto a web-side status, so "how far behind is web?" is a
lookup rather than a re-survey.

**This ledger does not override [ADR-0004](./decisions.md).** The two repos
share the HTTP API contract and the user-data JSON formats, nothing else.
Feature parity is a _goal we chose_, not an obligation the contract imposes —
so a `n/a` row below is a correct outcome, not a gap being excused.

Status values:

| Status    | Meaning                                                       |
| --------- | ------------------------------------------------------------- |
| `done`    | Web has the behaviour.                                        |
| `partial` | Some of it exists; the row says which part is missing.        |
| `todo`    | Portable and wanted. Carries a rung (see the plan below).     |
| `n/a`     | Not portable, or deliberately not mirrored. The row says why. |

---

## The three categories

**A — contract obligations.** The shared surface from ADR-0004. Drift here is a
correctness bug in a way a missing feature is not: desktop and web write the
same files and speak the same wire, so a schema either matches or silently
corrupts round-trips. One row in this category is overdue.

**B — portable features.** Desktop shipped a product behaviour that web's
surface could carry. Ordered below by value per line of change, not by ADR
number.

**C — not portable.** Rust/Tauri/packaging/OS-integration concerns, plus the
things web already decided against with a recorded rationale.

Each rung is a normal cycle: local issue under `.claude/issues/`, failing test
first, minimal implementation, docs updated in the same commit, `git push` left
to the maintainer per baseline §6.

One method note carried out of rung 1, because it changes how the remaining
rungs should be read: **the ADR text is a summary, and at least once it was a
summary that omitted a behaviour web had to match** (ADR-0027's prose does not
mention the 64 KiB write cap, which lives in Decision 10 and is visible in
`AiRecordWire::from_entry`). Where a rung says "mirror ADR-NNNN", read the
shipped Rust, not only the decision record.

Rung 2 is the second data point, and it cuts the other way: **this ledger was
wrong about web three times in one rung.** ADR-0024 had no web surface at all,
ADR-0071 was already satisfied, and ADR-0081's gap was real but differently
shaped than recorded. All three were settled by reading `apps/api/src`, none by
re-reading desktop. So the rule is symmetric — before starting a rung, re-derive
its rows from both codebases, and treat the row text as a hypothesis.

Rung 3 is the third data point, and it repeats rung 2's lesson on the desktop
side rather than the web side: **half of one row was not portable at all.**
ADR-0083 bundles a sidebar divider with a popover placer, and web has no
popover to place — the row above says so now. Re-deriving a rung can shrink it,
not only grow it, and a slice deleted for a stated reason is a better outcome
than a module with no consumer.

Rung 4 is the fourth data point, and it names the failure mode the first three
only circled: **a row can be right about the destination and wrong about what
stands between here and it.** ADR-0028's row said "sets `has_describe_table`",
which is true and was the whole point — but web resolves capabilities from the
bootstrap adapter, not from the connection in front of the user, so setting the
flag on `PostgresAdapter` would have changed nothing anyone could observe. The
per-connection capabilities route is not an extra; it is the reason the flag
means anything. Nothing in either ADR could have surfaced that, because desktop
has one backend at a time and never had the problem. **So re-deriving a row is
not only asking "is this still true?" but "what does web have to already be
true for this to be visible?"** — and the answer lives in web's divergences
from desktop, which are recorded above rather than in any ADR.

**Rungs 6 and 7 are not "more of the same."** Rung 6 gives web a write path it
has never had, and rung 7 adds engines whose dialects web has never parsed.
Both deserve their own decision entry before any code, not just an issue.
