Three things worth carrying forward rather than leaving in the ticket:

1. **v:1 byte-identical round-trip was given up deliberately.** The brief requires v:1 to load as v:2, which makes re-emission produce v:2 bytes; the `0018` assertion narrows to "v:1 in, canonical v:2 out". 2. **A parity gap was invisible in the ADR and visible only in the Rust.** ADR-0027's prose does not mention that writers cap `prompt` / `response` at 64 KiB (Decision 10, implemented in `AiRecordWire::from_entry`). 3. **Byte-compatibility is now demonstrated, not argued.** The desktop-emitted fixture re-exports byte-for-byte through `ExportHistory.stream()`, AI record included, which settles the key-order question that previously rested on reasoning about Zod's normalisation.

One gap stays open and is owed by desktop: the fixture's emitter constructs exactly one AI record, `status: "ok"`. `error` and especially `cancelled` are uncovered — web never _writes_ `cancelled` (no abort path on a non-streaming surface), so its read support for that status is currently validated only against objects web itself built. Filed back as [`handoff/2026-08-04-ai-fixture-cases-outgoing.md`](./handoff/2026-08-04-ai-fixture-cases-outgoing.md) per brief 0008 § Notes rather than papered over with a hand-written line.

**Rung 2 — adapter correctness** (ticket [`0024`](./issues/0024-adapter-correctness.md), `72bf120`). The bug rung: four desktop ADRs that each cost something in production and none of which add a feature. Re-deriving them against the shipped code before writing a line changed the scope of three of the four, and the corrections are the more useful artifact. ADR-0070's text-protocol pin was already true by construction but unpinned, so the fix is a runtime rejection of a `binary` column format rather than a test; ADR-0081's gap was worse than the ledger said (`query_timeout` is client-side only — the server kept running the statement after the client gave up), so `statement_timeout` now resolves alongside it from the same budget; ADR-0071's unreadable-table sweep **has no web analogue** and ADR-0024's at-rest `chmod` is **not applicable** to an in-memory store, both closed as no-ops with the reason written down.

**What rung 2 found that the survey did not: an unhandled-error crash on idle pooled connections.** Not on any desktop ADR, not in the ledger, and not visible by reading the adapter — the new integration tests shifted teardown timing and the suite reported 25 passing while exiting 1. Two isolation runs proved the defect predates the ticket: a pooled client that errors while idle has no in-flight query to reject, so pg emits `'error'` on the Pool, and with no listener Node takes the process down. The triggers are routine — a database restart, an admin terminate, a pooler recycling an idle connection (Neon and Supabase both do). A Neon connection sitting idle overnight could have killed the API. Fixed with `attachIdleClientErrorHandler`. The lesson worth carrying: **a green test count with a non-zero exit code is a finding, not a formatting problem.**

**Rung 6a — inline cell editing** (ticket [`0028`](./issues/0028-inline-cell-editing.md), ADR in [`decisions.md`](./decisions.md), six slices, five commits `82c6322` … `71ddf8f`). **Web is no longer read-only.** Landed: `useRowUpdate` over rung 5's `POST /connections/:id/rows`, `useEditContext` resolving the browsed table's primary key, a grid that stages edits and saves a row at a time, `CellEditorDialog.vue` for values the inline input cannot hold, and `result.edit.*` across all 11 locales.

Rung 6 was split at this point on purpose. Dump, restore and annotations are risky in the ordinary way; this half changes what the product is, so it wanted its own gate.

**Re-deriving the rung moved its target ADR, and the ledger row was pointing at the superseded one.** The survey named ADR-0042, which identifies a row by primary key and falls back to the engine's rowid when there is none. ADR-0063 supersedes it and removes the fallback. That is the half a web client must not port anyway — a rowid is stable only within a session on some engines, and web's request/response cycle has no session to be stable within — so a keyless table is read-only here and the grid says why. Reading ADR-0087 first is what surfaced it: its rule that a write names its rows by key rather than by position is what makes 0063 the target.

Three decisions worth carrying past this rung, all recorded in the ADR:

1. **Editability is provenance, never SQL parsing.** Only a schema-browser browse sets `sourceTable`; nothing inspects the statement. Every parser is one `JOIN`, one CTE, one view away from offering to write rows it cannot locate, and that failure is silent until it writes to the wrong table. The cost — a hand-typed `SELECT * FROM users` is not editable — is the right side to be wrong on.
2. **"No key" and "we could not ask" are different states.** Desktop swallows a failed describe into an empty primary key, which reads as a claim about the table. Web reports only the first; a describe that failed says nothing, because it learned nothing.
3. **A failed save keeps the staging.** Keyed on the original row index (rung 3's sort is a permutation), so a rejected write is corrected and retried rather than retyped. This is the behaviour most likely to be dropped quietly by a later refactor, so it has its own test.

Two places the mirror is deliberately narrower than desktop, written down so a later rung does not "fix" them back: the read-only note above, and Save re-running the browse statement rather than desktop's `reloadAfterSave` re-running the editor. `docs/api-contract.md` has a zero diff against `86b324f` — four rungs running.

**Rung 6b, restore half — a logical restore over HTTP** (ticket [`0030`](./issues/0030-logical-restore.md), ADR in [`decisions.md`](./decisions.md), seven slices, six commits `0d6975d` … `7456f3f`). **Rung 6b is closed and `has_atomic_restore` is `true` — every rung-0 capability flag now reads `true` for Postgres.** Landed: a lexical `splitStatements` that keeps dollar-quoted bodies, string literals and comments intact; a `planRestore` classifier; `executeBatch` on the adapter port running one pooled client inside `BEGIN` / `COMMIT`; a `RestoreDatabase` use case; `POST /connections/:id/restore/plan` and `POST /connections/:id/restore`; and a `RestorePanel` beside the dump button with `restore.*` across all 11 locales.

Four divergences from desktop, all deliberate. **Layer 2 is a leading-keyword classifier and web adds no SQL parser** — desktop uses `sqlparser`, but four of the five labels are informational and the one that changes behaviour (`transaction_control`, stripped because the runner owns the boundary) is exactly what a leading-keyword test gets right; a PL/pgSQL body full of `BEGIN … END` never reaches the classifier alone, because layer 1 keeps it intact and the statement arrives with `CREATE` in front. Desktop's stance is kept whole: never drop, never reject, label `unparsed` and run it verbatim — the deliberate inverse of the read-only check, which fails closed. **`application/sql` gets one allowance**, on the restore paths only, with its own 16 MiB limit that is explicitly not contract-pinned; `/query` still answers 413 at 70 KiB and `http-contract.spec.ts` asserts it. **The script crosses the wire twice** — ADR-0065's re-plan-on-run has no file to re-read here, and staging the upload server-side would be a second and much larger piece of process state than the connection registry, needing eviction, a size budget, and an answer for two tabs at once; `run` takes no plan parameter, so a stale plan has no path in. **Cancellation is a client disconnect** — the listener is registered before the preflight (a client that hangs up while the target is being queried should not have a restore start behind it), and because an aborted request returns no body, `cancelled` is a state of its own rather than desktop's flag on an outcome that here never arrives.

**The idiom from the dump half recurred, so it now has a name: plan returns the detail, run returns the sentence.** Desktop's `TargetNotEmpty { existing }` carries the table names; web's error envelope carries `category` and `message` and nothing else, and that is contract. So the plan response carries `existing_tables` and `is_target_empty` as ordinary data and the refusal is a 400 naming the count — the panel already holds the list. ADR-0050's warn-and-allow split the same way. Any future desktop refusal carrying structured data will hit the same wall, and this is the shape that gets through it.

Two things recorded so a later sweep does not remove them. **The atomic batch must use one pooled client**: `pool.query` per statement would scatter `BEGIN`, the body and `COMMIT` across different connections and the batch would stop being atomic while every unit test still passed — the integration test that catches it is `leaves nothing behind when a statement partway through fails`. And **the per-statement path was dead code when it was written**: Postgres advertises `has_atomic_restore` and was web's only real adapter, so the non-atomic branch was unreachable until rung 7 brought D1, whose HTTP API has no multi-statement transaction — which is why desktop has the branch at all. It stopped being dead code on 2026-08-06: `restore-database.d1.spec.ts` drives `RestoreDatabase` with a real `D1Adapter`, so the runner picks the branch itself rather than being told to by a fake.

**Rung 7 slices A and B — Turso / libSQL and Cloudflare D1 (2026-08-06).** Two adapters, seven planned slices; a driver-aware connection form was added as slice F once both drivers turned out to need fields the form cannot express. **Slice A** brought `TursoAdapter` over `@libsql/client` with `intMode: "bigint"`, which is the switch that keeps a 64-bit rowid intact. **Slice B** brought `D1Adapter` over Cloudflare's `/raw` endpoint behind a `D1Transport` seam, and the same precision question has no such switch there: `JSON.parse` has already narrowed every number to a double before the mapper sees it, so an INTEGER past 2^53 has lost its low bits. That is recorded in the mapper's doc comment rather than papered over — the fix is a reviver that reads the raw literal, and it is worth paying for only against a real database that hands back rowids that large. Three departures from desktop are deliberate and each has a reason web has and desktop does not: **the endpoint is a module constant** (desktop's configurable `base_url` exists for its own integration test, and here the same field would let a request body aim an authenticated call anywhere — the transport seam covers the testing role), **the two path ids must match `/^[A-Za-z0-9_-]+$/`** (they are interpolated into an authenticated URL, so `../../zones` would re-aim the call at another Cloudflare API — refused at the factory, which is the level a request actually reaches), and **a malformed body is a `ConnectionError` where desktop says `Query`** (the house rule from `turso-adapter.ts`: a 502 that turns out to be a bad query misleads far less than a 400 that turns out to be a dead server). What Cloudflare or SQLite decides is mirrored exactly, down to the `\_cf\_%` exclusion's `ESCAPE`, the `[code] message` join and its 2048-byte truncation, and the synthesised `no such table` text. The row cap stays out of both adapters: `ROW_CAP` is applied by `ExecuteQuery` after the adapter returns, so mirroring desktop's in-adapter `MAX_RESULT_ROWS` would cap twice and give one condition two unequal errors. **D1 is the first adapter whose capability flags read differently from its neighbours'** — `has_atomic_restore` false with no `executeInTransaction` method at all — which is what made rung 6b's per-statement branch reachable. Live suites sit behind env gates on both: `test/d1-integration.spec.ts` mirrors desktop's `rest_roundtrip.rs` behind `DBBOARD_D1_ACCOUNT_ID` / `_DATABASE_ID` / `_TOKEN` and self-skips with a printed reason, because D1 has neither a container to fall back on nor a `:memory:` engine, and baseline §15 puts the credential in the maintainer's hands — an unset run is the normal one. Gate green: API 945 passed / 3 skipped across 78 files, web 1096.

**Rung 7 slice C — MySQL / MariaDB and the dialect seam (2026-08-06).** `MySqlAdapter` mirrors desktop's crate over `mysql2` rather than sqlx, and two driver choices are what make that a mirror of behaviour rather than of shape: **`query`, not `execute`**, because the text protocol is what sqlx's `raw_sql` path sees; and **`typeCast: (field) => field.buffer()`**, because without it mysql2 decodes each cell by its _declared_ type and loses the distinction desktop keeps — a `BLOB` holding valid UTF-8 is text, a `VARCHAR` holding invalid UTF-8 is not. Metadata is decoded by the opposite rule on purpose: an information_schema cell that is not valid UTF-8 is a `SchemaError`, because a name the caller cannot address the object with is worse than no answer. TLS ends up hardened further than desktop's, since mysql2's default is no encryption at all where sqlx merely falls back to plaintext silently — absent, `PREFERRED` and `REQUIRED` all encrypt. It is the first non-Postgres adapter to advertise **`has_atomic_restore`**: MySQL's implicit commit on DDL would break the promise, but the logical dump is data-only (ADR-0049), so a restore script emits no DDL and an InnoDB transaction is exactly atomic. Desktop's `ping`, `foreign_keys` and `query_read_only` are absent rather than written and unused — the last carries three spellings of a statement timeout for a read-only route web does not have. `mysql2` cleared baseline §12 easily: MIT, pure JS, no install script, eight pure-JS transitive deps, and already in the lockfile as a transitive of nuxt's `db0`, so the tree gains an edge rather than a package. Unlike D1 the live suite needs no credential — `test/mysql-integration.spec.ts` starts a real `mysql:8` container, with `DBBOARD_MYSQL_URL` as an override.

**The seam turned out to want two types, and the survey's list of four places was wrong about one of them.** `apps/api/src/domain/dialect.ts` names `sqlite | postgres | mysql`; `apps/web/app/utils/sql-build.ts` names ADR-0072's own `ansi | mysql`. The API also emits _literals_, where SQLite and Postgres part company (`X'…'` versus `'\x…'::bytea`, `NULL` versus `'NaN'`), and the browser only ever emits identifiers, where they agree — collapsing them would import a distinction the frontend cannot act on. Of the four places the ticket's survey named, three took the parameter; `restore/plan.ts` emits no identifiers at all, and `dump/table-ddl.ts` — which the survey did not name — must _not_ take one, because the DDL it wraps is the server's own text and re-quoting it in another dialect would corrupt it. Both now say so in their module docs. The last mile was the one the survey called out: the driver reaching `SchemaBrowser.vue`. The SQL page finds it by matching the route id against `useConnections().list`, and **the option is getter-shaped** because that fetch usually resolves after the sidebar has mounted — reading a plain string once at setup would pin ANSI for the session and quietly break every MySQL sidebar whose connection list was a tick slower than the page. A test drives exactly that: mount with the driver absent, set it, assert the `LIMIT 0` probe back-quotes. Gate green: API 1029 passed / 3 skipped across 81 files, web 1134.

**Rung 7 slice D — the SSH tunnel (ADR-0069) with the liveness check (ADR-0092), five commits `f5fc7ae` … `3d9aa0c` (2026-08-09).** Bottom-up: the pure domain (host-key policy, fingerprint comparison, forward target), then the transport and the liveness wrapper, then the factory wiring, then the wire shape and the probe route. Mirrors `crates/dbboard-tunnel` at `main` = `b98f7a6` — the behaviour, not the driver, since desktop runs russh and web runs ssh2.

**Decision 2 is expressed as a type rather than as a check**, which is the part worth carrying: `HostKeyPolicy` has two variants and `resolveHostKey` demands exactly one, so a config naming neither fails to resolve instead of accepting whatever answers — there is no third variant for a later edit to reach for. `verifyHostKey` returns three verdicts because "your pin no longer matches" and "this host is not pinned yet" ask the operator for opposite responses, and ssh2 flattens both into "handshake failed"; the domain verdict wins over the driver's text, as desktop's `VerifyHandler` does. Three more things the driver leaves undecided are set in the transport: keepalives on (off is exactly what lets an idle tunnel die unnoticed), that rejection reason, and a probe timeout, because the probe is reachable from an HTTP route and a black-holed host would otherwise hold a request open as long as the TCP stack allows.

**The liveness check landed in `TunneledAdapter`, not in the registry, and the placement is forced.** Web keeps no keyring, so the only copy of a live connection's credential is inside the adapter serving it — the wrapper is the one layer that can rebuild a forward without asking the operator to re-enter one. Test-on-borrow past one keepalive interval; a failed `SELECT 1` tears down forward and adapter and reopens them once, even when two callers hit the same stale connection. Desktop's third part, a user-facing reconnect, has no web counterpart: there is no connection list item to re-arm, and the next request does it.

**The slice's own finding is the whitelist trap at its worst.** Everything above was unreachable over HTTP until the last commit, because the global `whitelist: true` pipe strips what no DTO declares — a body carrying an `ssh` block registered a perfectly ordinary connection and answered 201, with no error anywhere, going straight at the database the operator was tunnelling to reach. Slice A's `authToken` and slice B's `accountId` are the same trap and both fail closed; this one failed open. The DTO is a nested class with `@ValidateNested()` rather than a bare `@IsObject()`, because an object that is merely an object is un-whitelisted inside and `privateKeyPath` would survive at the door — web takes key _material_, never a path, so the API process never reads files off the server on request. `POST /connections/ssh/host-key` is the ADR-0076 half: it never authenticates (the key is captured and then refused) and never writes (the fingerprint fills a box for the operator to confirm), so pinning stays a deliberate act rather than trust-on-first-use behind a button.

**One divergence is recorded rather than closed.** Desktop's `SshEditInput::Keep` gives ssh secrets the blank-means-keep rule ADR-0080 gives the database password; web's `optionalText` maps `""` to `undefined` and then fails "exactly one of privateKey or password". Nothing submits an ssh block yet, so the blank cannot arrive until the form grows the fields — slice F, where the fix belongs. §12 cost nothing: ssh2 and its types were already in the lockfile as testcontainers transitive deps, so the tree gained **an edge, not a package** — though it did falsify the `ssh2: false` / `cpu-features: false` build-script justifications in `pnpm-workspace.yaml`, which claimed no SSH path was taken. Both rewritten; both denials stand, since ssh2's install script is a node-gyp rebuild of a bundled _optional_ crypto binding it carries on without.

## Known constraints

- Not a production SaaS — clarity and extensibility take priority over feature completeness.
- AI must remain optional and decoupled from core DB modules.
- A sibling project, `dbboard` (https://github.com/meta-taro/dbboard), is a **native Rust GUI** with its own **local Rust API**. It is an independent application — there is no runtime coupling and no shared code with `dbboard-web`.

## Relationship with `dbboard` (desktop, native Rust)

The same maintainer ships both clients, but they are independent applications:

- **No code is shared.** Each side writes idiomatic types, controllers, and UI in its own language.
- **The API contract is aligned by convention** — connection definitions, query envelopes, error categories, and AI provider request and response shapes use the same vocabulary on both sides.
- **User data formats interoperate** — exported connections and query history use a common JSON shape so a user can move state between desktop and web.
- **Independent schedules.** Either side may progress on any phase without waiting for the other. Phases are sized to be completable in a single focused session so context-switching never leaves either repo broken.
- See [decisions.md](./decisions.md) for the full policy.
