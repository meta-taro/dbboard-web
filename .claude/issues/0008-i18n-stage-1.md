# 0008 — Multi-language UI (Phase 2.5, Stage 1, 11 locales)

- **Status:** in progress
- **Phase:** 2.5
- **Opened:** 2026-06-03
- **Closed:** —
- **Branch:** `feature/phase-2.5-i18n`
- **Depends on:** [0006](./0006-pwa-shell.md) (code-merged) — i18n attaches to the same Nuxt shell.
- **Blocks:** _none — Phase 2 backend tickets (`0003` / `0004` / `0005`) work on `apps/api`, no file overlap._

## Goal

Make `dbboard-web` shell strings translatable so a user who installed the PWA can pick their language (English, Japanese, Korean, Simplified + Traditional Chinese, German, French, Spanish, Brazilian Portuguese, Russian, Italian — same 11 locales the desktop ships). The desktop sibling shipped this on 2026-06-03 as ADR-0015; the web side mirror is recorded as decisions.md "2026-06-03 — Multi-language UI support (Stage 1, 11 locales)".

The HTTP contract (`docs/api-contract.md`) is unchanged — translating the wire envelope would create contract drift with desktop. This phase touches **presentation only**: `apps/web` Vue components, the `<html lang>` attribute, and the locale switcher.

## Scope

1. `@nuxtjs/i18n@^10.4.0` wired into `apps/web/nuxt.config.ts` with the 11 locales declared in `apps/web/i18n/config.ts`.
2. JSON locale files at `apps/web/i18n/locales/<code>.json`. `en.json` is the canonical key set; every other locale must mirror it (parity test).
3. Resolution priority `?lang=` query > `dbboard_lang` cookie > `Accept-Language` > `en`, with `?lang=` enforced by a global route middleware (`app/middleware/locale-query.global.ts`).
4. `<html lang>` reactive to the active locale via `useHead({ htmlAttrs: { lang: locale } })` in `apps/web/app/app.vue`.
5. Locale switcher component (`apps/web/app/components/LocaleSwitcher.vue`) — `<select>` of the 11 locales, persists via the `dbboard_lang` cookie, touch target ≥ 44 × 44 (Phase 1.5 DoD).
6. Existing literal strings in `app/app.vue`, `app/pages/index.vue`, `app/pages/offline.vue` translated via `t("…")`. Keys mirror the desktop FTL set where applicable.
7. Tests pinning the locale set, the JSON parity invariant, and the helper narrowing.

## Out of scope

- **Arabic (`ar`) and Hindi (`hi`).** Browsers handle RTL + Devanagari shaping for free, but shipping them on web only would let the two clients drift in a way that is hard to undo. Stage 2 lifts both sides together — desktop ADR-0015 will be revisited at that time.
- **Server-side translation.** `apps/api` returns the contract error envelope in English (mirrors desktop's "DbError text stays English" rule). The `error.prefix.*` keys translate the _category_ label and prefix it to the English body — same boundary desktop draws.
- **Plural rules beyond what Vue I18n's native ICU subset covers.** Stage 1 messages use `{count}` / `{rows}` interpolation only; full ICU plural selectors land when an actual UI surface needs them.
- **Locale-aware number / date formatting.** Vue I18n exposes `$n()` / `$d()` but the current shell has no numbers or dates to format. Phase 4 (results grid) will pick this up when it ships.

## Handback

This phase has **no handback obligation** to desktop. The HTTP contract is unchanged, and desktop ADR-0015 explicitly allows the two clients to keep separate translation files. If a Stage 2 ADR lifts Arabic + Hindi later, the two sides should coordinate on naming and on whether Stage 2 ships simultaneously or staggered — but that conversation is for that future ticket, not this one.
