**Security hardening — API bearer-auth + localhost bind (`0016`) — landed on `develop` (2026-06-22).** Closes the two CRITICAL findings from the 2026-06-22 device-loss audit: every API route was unauthenticated and the API bound to `0.0.0.0` by default, so a LAN-adjacent attacker (e.g. on the same Wi-Fi as a stolen-but-locked laptop with the process alive) could `POST /connections` to register an attacker-controlled DB or siphon every executed SQL via `GET /history/export.jsonl`. New `apps/api/src/presentation/middleware/bearer-auth.middleware.ts` — Express middleware factory `createBearerAuthMiddleware(secret)`; when secret is undefined the middleware is a no-op (dev convenience), otherwise every route except `GET /health` requires `Authorization: Bearer <secret>` with a constant-time `timingSafeEqual` compare (short-circuits on length mismatch to avoid the throw). `apps/api/src/bootstrap/config.ts` gains `BIND_HOST` (default `127.0.0.1`), `API_SECRET` (empty-string normalised to undefined), and `assertSafeBindConfig({bindHost, apiSecret})` — throws when binding to a non-loopback address (`127.0.0.1` / `localhost` / `::1` / `::ffff:127.0.0.1` are loopback) without a secret, so network exposure and auth are coupled and a misconfigured deployment cannot reach `app.listen`. `createApp()` now accepts a `{apiSecret?}` override seam so the integration suite can inject a known secret without juggling `process.env` across test files (Vitest's `vi.resetModules()` does not reliably re-evaluate `config.ts` when other specs share the worker). `main.ts` calls `assertSafeBindConfig` first, then `app.listen(port, BIND_HOST)`. Web side: new `apps/web/server/api/proxy/[...path].ts` Nitro event handler — strips the `/api/proxy` prefix, builds the upstream URL against `runtimeConfig.apiUpstream`, injects `Authorization: Bearer ${runtimeConfig.apiSecret}` (server-only — `apiSecret` and `apiUpstream` live outside `runtimeConfig.public` so they never reach the browser bundle), and h3's `proxyRequest` streams the response body through unchanged (preserves the NDJSON history export). `runtimeConfig.public.apiBaseUrl` flips from `http://localhost:4000` to `/api/proxy`, so composables now make same-origin calls through the proxy. E2E `fixtures.ts` `DEFAULT_ORIGIN` updated to match. `.env.example` rewritten with `DBBOARD_BIND_HOST`, `DBBOARD_API_SECRET`, `NUXT_API_SECRET`, `NUXT_API_UPSTREAM`; the dead `CORS_ORIGINS` line (never read by code per audit finding 1-A) removed. New `docs/deployment.md` documents the threat model, env reference, localhost quickstart, LAN/Internet exposure recipe with Caddy auto-HTTPS, secret rotation runbook, and the device-level controls (full-disk encryption, screen-lock, remote-wipe) the codebase cannot replace. 241 (api) tests green — includes 8 config specs (`config.spec.ts`), 11 middleware specs (`bearer-auth.middleware.spec.ts`), 7 integration specs (`test/auth.integration.spec.ts`). Tracked by issue [`0016`](./issues/0016-api-auth-localhost-bind.md). No HTTP contract change (auth is transport-level), no UI strings touched. **Deployment posture is now safe for opt-in LAN exposure** — set both secret env vars + `DBBOARD_BIND_HOST=0.0.0.0`, put TLS in front, ship.

## Known constraints

- Not a production SaaS — clarity and extensibility take priority over feature completeness.
- AI must remain optional and decoupled from core DB modules.
- A sibling project, `dbboard` (https://github.com/meta-taro/dbboard), is a **native Rust GUI** with its own **local Rust API**. It is an independent application — there is no runtime coupling and no shared code with `dbboard-web`.

## Relationship with `dbboard` (desktop, native Rust)

The same maintainer ships both clients, but they are independent applications:

- **No code is shared.** Each side writes idiomatic types, controllers, and UI in its own language.
- **The API contract is aligned by convention** — connection definitions, query envelopes, error categories, and AI provider request and response shapes use the same vocabulary on both sides.
- **User data formats interoperate** — exported connections and query history use a common JSON shape so a user can move state between desktop and web.
- **Independent schedules.** Either side may progress on any phase without waiting for the other. Phases are sized to be completable in a single focused session so context-switching never leaves either repo broken.
- See [decisions.md](./decisions.md) for the full policy.
